StrmHub 完整使用文档

把 115 网盘变成你的私人影视库：视频不出网盘、本地只存 STRM 直链，TMDB 自动识别重命名分类入库、洗版与画质补全一条龙，Emby 秒刮削秒播，另带企微/TG 机器人与应用内自更新。

1这是什么 · 能做什么

解决什么问题

网盘存片有两个老矛盾：下载到本地费硬盘费带宽；网盘在线看没有海报墙、没有刮削、没有继续观看。StrmHub 的答案是把两头接起来——视频留在 115 网盘，本地只生成几乎不占空间的 .strm 直链文件，Emby/Jellyfin 刮削这些 STRM 就像刮削本地视频一样，点开播放时由 StrmHub 的 302 代理把播放器重定向到 115 直链，边下边播、零空间占用。

在此基础上，StrmHub 内建了一整套自动化流水线：网盘里的「待整理目录」放入新内容后，自动 TMDB 识别 → 重命名 → 分类入库 → 云端 SHA1 去重 → 洗版 → 画质补全 → 生成 STRM → 通知你，全程无需人工。

2核心概念与术语

五个关键词读懂 StrmHub，详细释义见文末术语表。

术语一句话理解
STRM只有一行 URL 的文本文件，扩展名 .strm。播放器打开它等于打开那行 URL 指向的视频——本地零占用
302 直链STRM 里存的是 StrmHub 自己的短链（http://IP:6086/d/xxx），播放器请求时 StrmHub 查台账把请求重定向到 115 真实下载地址
pick_code115 每个文件的唯一取件码，直链的参数就是它
台账（SyncedFile）「网盘文件 ↔ 本地 STRM」的对照表。删除/移动/改名都靠它精确定位，是整个系统的账本
生活事件115 官方的网盘操作流水（谁在什么时候上传/删/移/改名了什么），增量同步的数据源

3工作原理详解

整库流转全景

115 网盘→ 待整理目录→ TMDB 识别→ SHA1 云端去重→ 洗版判定→ 画质补全(可选)→ 模板重命名→ 媒体库(网盘内)→ STRM 落盘(本地)→ Emby 刮削→ 播放器 302 → 115

播放时发生了什么（302 直链）

  1. Emby 里点播放，Emby 读到的是 .strm 文件，把里面的 URL 交给播放端直接访问（DirectPlay，不转码不耗 Emby 资源）
  2. 播放端请求 http://服务器:6086/d/<pick_code>/文件名
  3. StrmHub 查台账拿到 pick_code，向 115 请求该播放端 UA 对应的下载直链（115 直链与 UA 绑定）
  4. 返回 HTTP 302 重定向 → 播放端直连 115 CDN 拉流
  5. 后续流量不经过你的服务器——服务器只出「一次重定向」，带宽压力≈0
💡这也解释了为什么直链有时效性：STRM 里存的是短链不是 115 直链，每次播放现取现 302，不怕 115 直链过期。

自动整理的判定顺序

整理对待整理目录里的每个条目依次做（任何一步有结论就结束）：

步骤说明不过时的去向
1. 提取标题从文件名/目录名解析片名、年份、季集无法提取 → 冗余
2. TMDB 识别搜片 → 拿标题/年份/类型/ID；失败再用目录名重试；仍失败走 GPT 提取（可选）搜不到 → 冗余；网络错误 → 留原地下轮重试
3. 云端 SHA1 去重按模板算出目标目录，列网盘该目录（含季子目录）比对 SHA1相同文件 → 已存在
4. 洗版判定台账里有同片记录时，按优先级规则比较新旧版本新版不优 → 已存在；更优 → 旧版移「洗版-旧版本」
5. 画质补全（可选）文件名缺分辨率/编码时 ffprobe 探测并改名探测失败 → 保留原名继续
6. 模板重命名按重命名模板改视频名，字幕/NFO 同步跟随失败 → 保持原名
7. 移入媒体库建分类目录/季目录 → 移动 → 广告与迷你视频进冗余—
8. STRM + 通知增量同步生成 STRM、刷新 Emby、推企微/TG（带海报，批量聚合）—

双通道：OpenAPI 与 Cookie

对 115 的所有读写操作走统一分发层：OpenAPI 优先、Cookie 回退。OpenAPI 是 115 官方开放平台接口（同 LitePan/QMediaSync 方案），签名鉴权、无 UA 风控、token 自动续期；Cookie 通道是传统 web/app 接口模拟，容易触发「服务器开小差」风控，保留作兜底。两者可同时配置。

Docker Compose 部署（推荐）

新建目录 strmhub，保存为 docker-compose.yml，然后 docker compose up -d：

services:
  strmhub:
    image: ghcr.io/daisyyijin/strmhub:latest
    container_name: strmhub
    restart: unless-stopped
    stop_grace_period: 20s        # 优雅退出窗口：SIGTERM 后程序停后台任务、
                                  # 冲刷待发通知再退出（约 3 秒收尾）
    ports:
      - "6060:6060"   # 管理后台（你自己用）
      - "6086:6086"   # 302 直链代理 + Emby 反代 + 企微回调（播放器/Emby/企微服务器访问）
    volumes:
    volumes:
      - ./config:/config           # ★ 全部配置：setting.yaml / auth.yaml(管理员) /
                                    #   jwt.key / 115-cookie.txt
      - ./data:/data               # ★ 数据库 strmhub.db（台账/媒体库/事件）
      - ./media:/media             # ★ STRM 本地目录（Emby 要挂载同一目录）
      - ./logs:/logs               # 日志 app.log（10MB 自动轮转 × 3 份）
      - /var/run/docker.sock:/var/run/docker.sock
                                  # 应用内自更新必需；不挂载则只能手动更新
    environment:
      - TZ=Asia/Shanghai
      - AUTH_USER=admin          # ★ 管理后台账号（环境变量管理，无网页注册）
      - AUTH_PASSWORD=change-me  # ★ 改成强密码，改后 docker compose up -d 生效

启动验证

  1. docker logs -f strmhub，看到 StrmHub 管理后台: http://localhost:6060 即正常
  2. 浏览器开 http://服务器IP:6060 → 用环境变量 AUTH_USER/AUTH_PASSWORD 配置的账号登录（未配置时首启自动生成随机密码，docker logs strmhub 查看）
  3. 云服务器记得放行两个端口的安全组/防火墙规则

可选：反向代理（HTTPS）

给管理后台套域名与 HTTPS 时，把两个端口分别反代即可。Caddy 示例：

admin.example.com {
    reverse_proxy 127.0.0.1:6060
}
emby302.example.com {           # 播放器/Emby 用的 302 域名（配到 STRM 直连域名里）
    reverse_proxy 127.0.0.1:6086
}
💡走 HTTPS 反代后，务必在「系统配置 → STRM 直连域名」填 https://emby302.example.com，否则生成的短链还是 http/IP 形式，会被浏览器当混合内容拦截。

6首次配置（四步）

登录后台后，仪表盘顶部的「配置引导」卡片会逐步点亮，四步核心完成后自动隐藏。以下为每步详解：

第 1 步 · 绑定 115 账号（账号管理）

  1. 推荐先在 open.115.com 申请一个应用拿 AppID（个人开发者即可，免费）
  2. 账号管理页把 「启用 OPENAPI」打开，填 AppID，点「保存并扫码授权」
  3. 用 115 App 扫码完成 OAuth 授权——之后 token 自动续期，基本一劳永逸
  4. （可选但建议）再点「二维码登录」补一个 Cookie 通道作为回退

第 2 步 · 填 TMDB API Key（系统配置 → TMDB配置）

  1. 注册 themoviedb.org（免费）→ 个人设置 → API → 申请 Developer Key
  2. 把 Key 填入保存；界面语言默认 zh-CN（搜索结果优先中文片名）
  3. 国内服务器：到「系统配置 → 代理配置」填代理（TMDB 识别/通知/GitHub 更新检查都会走它）

第 3 步 · 选整理目录（自动整理 → 基础配置）

  1. 待整理目录：新内容的落脚点（离线下载/转存/手动丢入）。建议建在媒体库内，如 影视库/待整理
  2. 已存在目录：重复内容去向，如 影视库/已存在
  3. 冗余目录：无法识别/广告/洗版旧版本去向，如 影视库/冗余
  4. 每个都点「选择目录」从网盘挑（支持手填路径自动换算 cid）
⛔三个工作区目录不要选在媒体库根或库的上层目录——否则排除区会覆盖整个媒体库，增量同步会熔断保护（日志明确提示），需改选为库内子目录或库外目录。

第 4 步 · 首次全量同步（Strm 管理 → 全量同步）

  1. 媒体库目录选网盘里规划好的库根（如 /影视库——注意与待整理是「包含」关系：待整理在库内）
  2. 本地路径默认 /media；后缀过滤用默认即可
  3. 点「开始全量同步」——任务条实时显示进度；完成后 media/ 里出现 STRM 树
  4. Emby 挂载 ./media 目录建库（详见 Emby 对接章），扫库出海报即成功
💡首次同步受 115 限速（读接口最快约 1 秒/次）影响，几千个文件的库约需十几分钟到半小时，属正常现象；之后增量同步只处理变化，秒级完成。

7账号管理（115）

通道一：OpenAPI（推荐）

项说明
怎么开通open.115.com 注册开发者 → 创建应用 → 拿到 AppID（一串数字）
怎么绑定账号页开「启用 OPENAPI」→ 填 AppID →「保存并扫码授权」→ 115 App 扫码

通道二：Cookie

  • 网页扫码（推荐）：点「二维码登录」，用 115 网页/App 扫码，自动取 Cookie；二维码过期自动续期
  • 手动粘贴：浏览器登录 115 后 F12 复制 Cookie 粘贴进来

API 请求间隔

所有 115 接口调用前的强制等待（默认 3 秒）。内部再分级：写操作（改名/移动/删除）强制 ≥3 秒，读操作（列目录等）约 1 秒。被风控时调大（如 5 秒）；追求整理速度且账号稳可微降。界面上的「连接诊断」可一键检测会话有效性/域名风控/UA 配对。

8全量同步与 STRM

做什么

递归遍历网盘媒体库：视频 → 本地生成 .strm；字幕/封面/NFO 等附属 → 实体下载到对应路径。每次运行是增量补齐（存在的跳过或覆盖），不会删除本地多余文件——清理走「Strm 管理 → 全量同步 → 失效 STRM 检测」（见第 10 章）。

参数详解（Strm 管理 → 全量同步）

参数说明
媒体库目录网盘库根。「选择目录」浏览挑选；手填路径（如 /影视库）会自动换算成 cid，路径与 cid 不匹配会拦截提示重选
本地路径STRM 落盘根目录，默认 /media（容器内路径，对应宿主机 ./media）
视频后缀哪些扩展名算视频（生成 STRM）。默认已覆盖主流格式含 iso
图片/数据后缀附属实体下载的白名单：图片（jpg/png/webp…）与数据（ass/srt/ssa/sub）+ NFO 自动纳入
整理工作区自动识别并排除待整理/已存在/冗余目录（它们不参与同步生成 STRM），配置卡上有✗提示的槽位需要重选

STRM 直链设置（Strm 管理 → STRM 配置）

设置选项与建议
直连域名302 短链的主机部分。默认留空＝按播放请求的 Host 动态生成（多数场景最优）；套了固定域名/HTTPS 反代后必须显式填，如 https://emby302.example.com
直连格式pick_code_name（推荐）：短链带原文件名，播放器显示与缓存友好；pick_code：仅取件码，链接最短
保留扩展名STRM 文件名是否带原始扩展名（电影.mkv.strm vs 电影.strm）。建议开——Emby 识别媒体格式更准
本地已存在时覆盖（推荐）：每次全量重写内容，改配置后能生效；跳过：存在即不动，最快但改配置不回填

一个 STRM 文件长什么样

执行与日志

  • 任务条实时显示阶段（遍历/落盘/完成）；进行中其他同步/整理按钮互斥禁用
  • 关键日志：全量同步开始 → 每目录 同步xxx（等 x.xs）（限速等待） → 全量同步完成（耗时… 视频 N（生成 STRM M）…）
  • 附属下载失败会计入失败数，下轮全量自动补
  • 全量结束会把「事件窗口」内的生活事件标记为已覆盖，增量只处理此后新事件

9增量同步

原理

拉取 115 生活事件流（网盘操作流水），按事件把变化映射到本地。事件处理规则：

事件本地动作
上传 / 收录 / 复制媒体库内 → 生成 STRM / 下载附属；工作区与库外 → 忽略
删除按台账精确定位删除对应 strm/附属与台账行；目录删除=整树清理
移动 / 改名旧位置按台账精确清理（无台账记录则跳过，绝不按文件名模糊删），新位置重建；网盘改名整理过的文件由此自动对齐
目录改名路径缓存失效后重遍历受影响子树重建
🛡️安全设计：删除类操作全部以台账为准精确执行；工作区（待整理等）内的事件不监控；移动/改名事件绝不使用「按文件名猜测」的删除——避免同名文件误删。处理失败的轮次不消费事件，下轮自动重做。

定时配置（轮询间隔）

增量是独立轮询：默认每 30 秒一轮，最小 15 秒（填更小按 15 处理）。一轮通常只发 1~2 个请求，没有新事件时完全静默，所以跑得勤的代价很低——手机上传的片子几十秒内就能出现在媒体库里。

🔗增量不跟着自动整理的 cron 走：整理是识别搬移改名的重操作，低频合适；增量只管网盘端的外部变更（手机/客户端上传、离线下载完成、网页端删改），要的是实时性。两条时间表互不依赖——整理自己写 STRM、自己刮削，它在网盘上做的搬移与改名会被登记下来，绕回事件流时增量直接跳过，不会重复处理。自动整理 Cron 在「自动整理 → 基础配置」。

间隔填 0 = 关闭独立轮询，退回旧行为：跟着自动整理的 cron 串行跑一次（逃生门，除非怀疑轮询本身有问题否则不用动）。

其他触发：页面上的「开始增量同步」按钮；企微机器人发「同步」；转存 / 离线下载完成时的自动整理跑完会顺手带一轮增量收尾。把间隔填 0 之后，就只剩这些触发加上「自动整理 cron 命中时串行跑一次」——那条 cron 也留空的话，增量就完全不会自动执行了。

水位与事件保留

  • 每轮成功后记录水位（时间戳），下轮从此续拉；失败不推进
  • 事件表保留 30 天自动清理——停用增量超过 30 天，期间的删除变化就丢了：恢复后先跑一次全量，再用「失效 STRM 检测」对齐（见第 10 章）
  • 参数（目录/后缀）继承全量同步配置，无需重复填

10失效 STRM 检测

失效 STRM ＝ 本地还留着 .strm 或附属文件，但网盘上的源文件已经没了。Emby 里条目照常显示，点开播放 404。

为什么会漏

  • 生活事件有窗口：网页版批量删除、事件识别不出来的删除动作，增量同步都收不到
  • 增量停机期间发生的删除（事件表只保留 30 天，过期即丢）
  • 你自己缩减了后缀白名单——原先同步过的文件不再属于同步范围，也会被判成失效（这是预期行为，但要让你看见）

这些漏掉的条目只有拿网盘当前完整清单和本地台账做一次差集才查得出来，而全量同步本来就会取回这份清单。所以检测挂在全量同步上。

怎么用（Strm 管理 → 全量同步）

  1. 打开「失效 STRM 检测」开关并保存配置
  2. 跑一次全量同步。结束时做差集，台账里有、本次清单里没有的条目被打上失效标记
  3. 页面出现「待清理失效 STRM」卡片：抽样列出前 50 条（路径 / 类型 / 大小 / 标记时间）与总数
  4. 确认无误后点「清理全部 N 个失效 STRM」——删除这些本地文件与对应台账记录，并顺带删掉因此变空的目录。网盘不受影响
⛔只标记，不自动删除。清单不完整（翻页短缺、目录表缺项）时算出的差集是假的，一删就是真丢数据——这种情况后端会直接跳过标记并在日志说明。另外失效占台账总数超过 20% 时页面会红色告警：这通常意味着上次扫描没取全，或你同步的不是平时那个媒体库，先重跑一次全量确认再清理。

定时全量（可选）

检测开关打开后，下方会多出 定时全量同步 开关与一个 5 段 cron（带未来触发时间预览）。它的用途就是定期刷新失效标记：

0 4 * * *          # 推荐：每天凌晨 4 点一次
0 4 * * 0          # 每周日凌晨 4 点一次
  • 整库扫描请求量大（115 风控敏感），建议每天最多一次、放在夜间；日常变化交给增量同步即可
  • 定时跑出来的结果同样只标记不删除——定时任务没人盯着，误判一次就是真丢文件
  • 「失效 STRM 检测」关掉时这个开关不显示，后台也不会执行：检测关着的时候定时全量纯属白跑一趟
  • 全量与增量的 cron 同一分钟同时命中时只跑全量（全量跑完会把事件窗口标记为已覆盖，再跑增量是重复请求）
💡典型用法：仪表盘「失效 STRM」数字变大 → 来「Strm 管理 → 全量同步」看待清理列表 → 确认后一键清理。想彻底放手就把定时全量打开，每天夜里自动对账，你只负责点那个确认。

目录规划建议

├── 冗余/       ← 无法识别/广告/洗版旧版本去向

12识别规则与 GPT

识别链（从文件名到 TMDB 命中）

  1. 清洗：剥掉【发布组】块与广告域名、替换规则逐条应用
  2. 解析：提取 标题/年份/季/集/分辨率/来源/编码/发布组（片名中英拆分）
  3. 搜索：原始标题带年份搜 → 不中去年份宽搜 → 清洗标题再搜 → 中英拆分组合搜
  4. 文件名失败：改用目录名重试（保留文件名的季集号）
  5. 仍失败（可选）：GPT 从原始文件名提取「片名+年份+类型」后再搜一轮

替换规则（识别配置）

一条规则就是「把 A 换成 B」，B 留空 = 删掉 A。界面上一条一行地加，每条自己选 文本（一模一样才替换）还是正则（中间内容不固定时用）。 不知道写什么就点「常用规则」勾几条现成的——去【】宣传块、去站点水印前缀、去字幕语种标注等都在里面。

规则作用
【[^】]*】 → 空（正则）删掉发布站塞在最前面的整块广告
^(?:www[.])?[A-Za-z0-9-]+[.](?:com|cc)@ → 空（正则）删掉 www.xxx.com@ 这类域名水印前缀
4K修复版 → 4K（文本）固定的词直接换掉
([0-9]{4})年 → $1（正则）替换内容里可以用 $1 引用捕获组
⚠️ 规则从上往下依次套用，后一条作用在前一条的结果上（所以「收敛连续的点」要放最后）。 后端用 Go 的 RE2 正则，不支持先行/后行断言与反向引用，写了这些的规则整理时会被整条跳过（界面上会当场提示）。 页面上的「效果预览」可以直接粘一个真实文件名试算，看命中了哪几条、结果长什么样。
💡 替换只作用在送去识别的那份名字上，不改网盘里的文件名； 入库后叫什么由重命名模板决定，画质/编码/发布组也仍从原始文件名提取。

其他识别配置

配置说明
最小体积小于该 MB 数的视频不识别、不入库，直接进冗余——过滤广告片/预告/引流视频。0=不限制，建议 50~200
发布组名单系统默认只认「文件名末尾 -GROUP」；名单里的组名在文件名任何位置出现都算命中（要求是完整片段，填 CR 不会误伤 CRUNCHYROLL）。用于 {resource_team} 变量与洗版的 resource_team 匹配

GPT 辅助识别（GPT识别 Tab）

给「文件名混乱、TMDB 直搜失败」的内容兜底：把原始文件名交给大模型，让它提取规范片名 + 年份 + 电影/剧集，再回到 TMDB 搜索。配置：

  • API 地址：OpenAI 兼容接口即可，推荐国内平台（硅基流动等）填其 /v1 地址，无需代理
  • Key / 模型：对应平台的密钥与模型名（如 deepseek-flash 等便宜模型即可胜任提取任务）
  • 只有前面所有搜索策略都失败才会调用，日常几乎不消耗额度

13重命名模板

两种语法

① 变量 {xxx}

直接替换为识别/解析值（见下表）。

② 条件块 <…>

块内所有变量非空才输出整块，任一为空则整块丢弃——可选段的正确写法：

{title}.{year}<.{resource_pix}><.{resource_type}><-{resource_team}>{ext}

# resource_pix=2160p、type=BluRay、team=TnT 时：
蜘蛛侠.2022.2160p.BluRay-TnT.mkv
# pix 缺失时（整块丢弃，不残留点号）：

⚠️块必须闭合（有 < 就要有 >）；分隔符写在块内（<.{pix}> 而不是 .<{pix}>），空块丢弃时才不会留下孤点。非法字符自动清洗，连续点号自动收敛。

16洗版策略

是什么

同一部片来了「新版本」（比如已有 1080p WEB-DL，又下载了 2160p BluRay）时，按你定的优先级规则自动判断谁留下谁让位，输家移入冗余/已存在下的 洗版-旧版本/<片名>[/Season xx] 子目录，并可推送「🔄 洗版替换」通知。

配置 YAML 全字段

电影洗版策略:
  mode: replace            # coexist=多版本共存 / skip=有就不收 / replace=按规则替换
  scope: all               # all=全局只留一个最优 / group=按分辨率分组各留一个
  media_type: movie        # 本策略适用的类型（movie/tv）
  category: ''             # 限定二级分类（逗号分隔，空=所有）
  old_version_target: redundant   # 旧版去向：redundant=冗余 / existing=已存在
                           # （delete 也按冗余处理，不做网盘真删除）
  priority_level:          # ★ 优先级规则，从上到下，第一条能分出高下的定胜负
  - resource_team: "WiKi"          # 发布组
    resource_effect: "!DV.HDR,!DV" # 特效；! 前缀=排除
  - resource_pix: "2160p"          # 分辨率
    resource_type: "BluRay"        # 来源质量
    resource_effect: "!DV.HDR,!DV"
  - resource_pix: "1080p"
    resource_type: "BluRay"

剧集洗版策略:               # 剧集按「同一集」比较：新集数=新增直接入库，不参与洗版
  mode: replace
  media_type: tv
  priority_level:
  - resource_pix: "2160p"
  - resource_pix: "1080p"

可用比较字段

字段示例值说明
resource_teamWiKi, TnT, FRDS发布组（配在识别配置的名单里更准）
resource_pix2160p / 1080p / 720p分辨率
resource_typeBluRay / WEB-DL / HDTV来源质量
video_encodeH265.10bit / REMUX视频编码
audio_encodeTrueHD.7.1 / DTS音频编码
resource_effectDV.HDR / HDR10+ / !DV特效；! 前缀表示「命中即排除」

判定算法说明

  1. 取库内同片文件作为「旧版」：剧集取同一集的文件，电影取第一个视频文件（跳过海报/NFO）
  2. 逐条过优先级规则：新版命中且旧版未命中 → 新版胜；反之旧版胜；都中/都不中 → 看下一条
  3. 规则全部平局：保守判定新版不优（不折腾）
  4. 新版胜 → 旧版移走、清对应台账，新版正常入库；旧版胜 → 新版进「已存在」
  5. scope: group 时先比分组：分辨率不同的版本直接共存，同组内才按规则比

示例解读

上面默认配置的效果：WiKi 无 DV 的版本 > 2160p 原盘 > 1080p 原盘——即「不要杜比视界的 4K，宁要干净的 1080p 原盘」的一种典型偏好；你可以按喜好改排序。

17媒体补全

什么时候探测

文件名缺分辨率或缺编码（如 蜘蛛侠.2016.mkv、白头山.2019.1080p.mkv）时触发。开启后整理时同步探测：拿 115 直链 → ffprobe 读头部几 MB → 拿到真实分辨率/编码/音轨/HDR → 改名 → 再走模板重命名入库，一步到位。也可随时发企微指令「补全」扫描整个媒体库的存量文件（队列 30 秒/个温和处理）。

决策矩阵（自动整理 → 媒体补全）

情形默认可配
名缺画质 + 探测有 → 补齐改名可改为保留
分辨率相符，但缺编码 → 补编码改名跟随上项
名实一致（都对得上）保留固定保留
名实冲突（名 1080 探到 2160 / 反之）按探测改可改为保留
冲突跨 2 档（720 ↔ 2160）保留固定（疑似探测异常的防御）
命名已完整（有来源+发布组）保留激进模式可改
探测失败保留原名继续整理固定

三种预设模式：保守（尽量不动名字）/ 标准（推荐） / 激进（完整命名的冲突也重排）。三个可配项留空即跟随模式默认。

探测失败的常见原因

  • MP4 的 moov box 在文件尾（未做 faststart 优化）——头部探测拿不到元数据，保留原名不影响入库
  • 直链偶发风控——探测失败的文件保留原名，下次整理/扫描会自动重试（失败任务自动复活重试最多 3 次）

25常见问题

必须用 VIP 账号吗？

不强制，但离线下载/高频 API 对免费账号限制更严，风控也更敏感。重度使用建议 VIP。

STRM 会占多少本地空间？

单个 strm 只有几十字节（一行 URL）。附属文件（字幕/封面/NFO）是实体，视库大小一般几百 MB 以内。

可以和 AList/OpenList 共用同一个 115 账号吗？

可以，但要意识：多处同时高频调用会共享风控额度。建议错峰，或重要任务走 OpenAPI 通道。

为什么整理/同步这么慢？

115 有接口频率限制，全局限速是防风控的保护（读约 1 秒/次、写强制 ≥3 秒/次）。首次全量几千文件约十几分钟属正常；日常增量秒级。

外网播放卡吗？

播放流量走 115 CDN 直连，不经过你的服务器——速度取决于 115 给该文件的下载速度与你本地带宽，和 StrmHub 服务器基本无关。服务器只出一次 302。

重新放回同样的文件还是提示「已存在」？

去重按网盘目标目录里的 SHA1 比对：你删了库里的 A 文件，但目标目录还有同 SHA1 的 B 文件（或内容被移进了「已存在」目录）。清掉目标目录/已存在目录里的同内容即可。

网盘手动改了名，本地 STRM 会更新吗？

会——增量同步的「改名/移动」事件会删旧建新；没开增量就跑一次全量，再用「失效 STRM 检测」清掉残留。

整理后字幕没挂上？

字幕必须与视频同基名（语言后缀保留，如 片名.chs.srt）。整理会自动跟随改名；自己后放的字幕注意命名要与视频一致。

画质补全探测失败有害吗？

没有——失败保留原名继续入库。常见原因是 moov 在文件尾的 MP4 拿不到头部元数据；任务会自动重试 3 次。

更新后要求重新登录？

升级到「JWT 密钥随机化」版本时会重新生成密钥，旧登录态失效一次——重新登录即可，之后不再发生。

机器人菜单没出现？

保存消息配置会自动生成；企微客户端有缓存，退出该会话重进一次。

识别失败的文件去哪了？

「冗余」目录。人工把文件/目录改成更规范的名字（带片名+年份）再丢回待整理即可重试；网络原因失败的会留在待整理自动重试。

支持别的网盘吗？

当前 115 专属；界面上「规划中」的卡片即未来方向（OpenList）。

忘记管理员密码 / 想改密码？

账号由环境变量 AUTH_USER/AUTH_PASSWORD 管理：修改 compose 里的值后 docker compose up -d 重启即生效。或执行 docker exec strmhub ./strmhub --reset-admin 删除凭据文件，重启后按环境变量重建（未配置环境变量则生成随机密码，见启动日志）。

如何完全重置？

停容器删掉 config/ 与 data/ 再启动＝全新安装；media/ 建议一并清空重同步。只重置管理员：改 AUTH_USER/AUTH_PASSWORD 重启，或 docker exec strmhub ./strmhub --reset-admin 后重启重建。

多个人能用吗？

管理后台单管理员（个人工具定位）；Emby 侧多用户由 Emby 自己管理。

只含一行 URL 的文本文件（扩展名 .strm）。播放器把它当作「重定向到该 URL 的媒体」播放——Emby/Jellyfin/Kodi 原生支持。
302 直链 / 短链
StrmHub 代理地址（6086/d/<pick_code>）。播放器请求它，服务端即时换取 115 真实直链并返回 HTTP 302 重定向。好处：STRM 内容永不过期、播放流量不过服务器、直链按请求端 UA 正确签发。
pick_code
115 文件的取件码，网盘侧每个文件唯一，短链与取流都靠它。
TMDB
The Movie Database，影视元数据库（标题/年份/海报/分类/评分）。识别、命名、分类、入库通知的元数据来源。
SHA1
文件内容指纹。去重与秒传的基础：相同 SHA1 = 相同内容（不论文件名）。
洗版
同一部片存在多个版本时按优先级规则择优保留、旧版归档的策略。
画质补全
用 ffprobe 读取视频真实参数（分辨率/编码/音轨/HDR）补进文件名的过程。
台账（SyncedFile）
「网盘文件 ↔ 本地 STRM」对照表，删除/移动/改名的精确定位依据。
生活事件
115 官方操作流水（上传/删除/移动/改名…），增量同步的数据源，保留 30 天。
OpenAPI
115 官方开放平台接口（open.115.com），应用凭 AppID+OAuth 授权访问，无 Cookie 风控。
